# 事故复盘 2026-10-11 — "我这边正常，客户那边点不了"

> 一天三起连锁事故的完整因果链与修复记录。这份文档的价值不在结论，在排查路径：
> 每一步"看起来像的原因"是怎么被证据排除的。同类问题再发生时按此顺序查。

## 背景

- 客户反复反馈：主控端连上被控端后**点击没反应**（关不掉窗口、最大化无效、"它弹出了"）。
- 同一个人（开发者本人）在自己机器上连同一台被控端**一切正常**——问题只出现在客户那台主控机上。
- 关键环境事实（排查中途才确认）：**客户的主控机与被控端在同一个局域网**（192.168.1.x）。

## 事故一：点击被"主屏监视模式"静默吞掉（中午 13:41）

### 现象与证据

worker 日志（时间线，被控端侧）：

```
13:40:14-16  主控端 2 秒内 5 次重连（重建码流风暴）
13:40:19-27  3 次点击到达，正确路由"真实光标"
13:40:47     WGC 10s 无新帧 —— 画面冻结，用户对着旧图点
13:41:00     主控端把画面切到 PrimaryOnly（主屏 = 整屏只读！）
13:41:03     主控端请求把(383,305)的窗口搬到外屏 → 被拒（那是桌面外壳窗口）
13:41:09     切回 VirtualOnly
13:41:32     用户放弃点击，改用"打开此电脑"（第 20 个 explorer 窗口！）
```

### 因果

「画面」下拉框切到**主屏**后整个画面只读（隐私设计：只监视不动手），左键点击被换成
"把窗口搬到副屏"指令，点桌面还会被拒——**界面上毫无反应**。"它弹出了"就是只读提示气泡
或窗口被搬走的动作。网络一卡用户就去动设置，掉进这个陷阱。

### 待修（UX）

主屏模式切入要弹确认/常驻遮罩横幅，状态栏小字不够。断线要盖"已断线"横幅而不是停留旧帧。

## 事故二：UDP 打洞直连单向黑洞（下午，当日主案）

### 现象与证据

客户机 viewer 日志（拿到这份日志是破案转折点）：

```
P2P 直连成功：192.168.1.48:47890 —— 视频走直连
UDP 打洞成功（RTT≈0ms）—— 视频/输入改走直连，中继保底
[90 秒后] P2P 直连已断开 → 被拒绝 → 重连成功
已 3.0s/8.0s/…/33.0s 没有解出画面（被控端采集 21.4fps 正常！）
```

被控端协调器日志：

```
14:45:06 UDP 打洞成功（RTT≈0ms，视频/输入改走直连）
14:45:08→28 [诊断] 直连=已建立(..., 0帧/0KB)   ← 整个会话 0 帧发出
14:45:25 用户退出
14:45:32 UDP 直连判死（3.5 秒无对端流量）：第 4 次
```

整个 23 秒会话 `[input]` 零条——**双击、点关闭全部发进了黑洞**。

### 根因（三个缺陷叠加）

1. **传输层**：同局域网打洞秒成，但"被控端→主控端"方向对大 UDP 包单向丢弃
   （小包 ping/HELLO 通、1208B 视频分片和输入消息全丢；疑似 MTU/行为管理设备，
   需现场抓包才能定案）。
2. **决策层**：`SendVideo` 只看 `_live` 标志就返回成功，不校验送达；切换路径没有
   对端确认的探针。
3. **观测层**：RTT 显示值是两台机器 `TickCount64`（各自开机毫秒数）相减——跨机器
   毫无意义，"RTT≈0ms"是从未确认过往返的默认值；诊断行只统计 TCP 直连计数器，
   UDP 的收发字节看不见。"通道看着活着"就是这么来的。

### 为什么开发者那边永远正常

开发者的网络到被控端不走同网段，打洞不成立 → 全程 TCP 中继/直连 → 稳定。
**同一个软件，好网络上一切正常，坏网络上进入另一种沉默失败模式**。

### 修复（1.5.29）

`UdpPunchEnabled=false` 默认停用整个 UDP 打洞（要约不发了，主控端不会开打洞窗口），
视频/输入统一走 TCP。同网段用 TCP 直连（47890）带宽延迟同样够。诊断行补
`UDP={帧数/发送KB,收KB}` 计数。根因查明后可用配置开回。

## 事故三：H.265 编码器缓存错配（晚上 21:18）

### 现象与证据

HOT 重装（新安装包）后主控端黑屏，提示"虚拟外屏丢失"。翻日志发现两层：

```
实际采集目标：DISPLAY5 <Virtual Display Driver>（重启后恢复）
启动 ffmpeg：h264_qsv（H265）…        ← H.264 编码器配 H.265 封装
hevc muxer supports only codec hevc → ffmpeg 秒退 → 重建 → 无限循环 0 帧
```

### 根因

`FfmpegEncoder.ResolveEncoder` 缓存键 `{ffmpeg}|{配置}|{分辨率}` **缺编码族维度**：
白天 H.264 会话把 `h264_qsv` 缓存，晚上客户装的新主控端（1.2.7，首个会上报
H.265 解码能力的版本）触发协商切 H.265 → 同键命中 → 拿到 H.264 编码器配
hevc 封装 → 秒崩循环。**这条路此前从未被真实触发过**（旧主控端/测试脚本都不发能力上报）。

"虚拟外屏丢失"是重装后 VDD 未挂载的独立问题，重启机器解决。

### 修复（1.5.30）

缓存键补编码族 `{ffmpeg}|{配置}|{h264|h265}|{分辨率}`；三台在线被控端热更到 1.5.30；
另把三台 `VideoCodec` 钉到 `h264` 作双保险（验收后可改回 `auto` 释放 H.265 带宽收益）。

## 排查方法论（值得复用的部分）

1. **先问"点击到底有没有到被控端"**——`[input] 点击按下(x,y) → 路径` 打点（1.5.24 加的）
   一眼分流："到了但路由错" vs "根本没到"（投递问题）。本案两次都是后者/传输层。
2. **两侧日志对时间轴**——viewer 日志（连接状态/解码器/打洞）× 被控端日志（接入/重建/[input]）
   拼出完整因果链。拿不到 viewer 日志前走了很多弯路。
3. **中继 `/api/agents` 的 connectedAt 是免费的观测点**——被控端链路稳不稳、谁在线，
   一条 curl 的事。本案靠它排除了"被控端掉线连坐"。
4. **诊断行必须覆盖所有活跃路径**——UDP 收发计数这次是盲区，事后补上。
5. **手机照片截图可以做几何分析**——壁纸配色比对（蓝 vs 白）能确认用户连的是哪台机器。
