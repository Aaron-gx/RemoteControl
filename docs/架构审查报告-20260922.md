## 三、详细说明与优化建议

### P1-1 架构一致性：重大架构转向未收敛

**问题概述**

项目经历了从「RDP 多会话独立方案」到「单会话共享 + 双光标方案」的**重大产品转向**，但代码、文档、脚本三者没有同步收敛，形成三套并存。

**详细说明**

- **策划方案（cehua.txt）**：核心是"本地 Session 0 + 远程 Session 1 两个独立桌面、两套鼠标、互不干扰、可无人值守"，依赖 `RDPWrap` + `RemoteWorker` 用户 + 虚拟副屏。
- **客户需求变更**（见 `docs/架构-单会话共享与双光标.md`，2026-09-22 定稿）：客户要求**副屏必须共享管理员账户数据**（同一份微信/文件/profile），因此多会话方案**被判定作废**，产品形态**只有一种**：同账户 + 虚拟外屏 + 双光标（本机独占真实光标，远端后台定向注入）。
- **但代码里旧实现仍完整保留**：
  - `RdpSessionManager.cs`（33 KB）、`SessionLauncher.cs`（13 KB）——完整的 RDP 会话管理逻辑仍在；
  - `AgentConfig` 仍保留 `WorkerUser / WorkerPassword / RdpLoopbackHost / UseRdpSession` 等全套多会话配置字段；
  - `install-agent.ps1` 仍提供 `-MultiSession` 开关（仅加了个 `-IUnderstandLegacyMultiSession` 逃生门）；
  - `create-remote-user.ps1`、`RDPWrap/` 驱动、`drivers/RDPWrap/` 全部仍在。
- 新实现 `EnforceProductMode()` 会在载入配置时把旧多会话配置**强制改回共享模式**——这是"运行时打补丁"，属于**防御性兜底，而非架构收敛**。

**为什么是问题**

1. 旧代码路径仍可被触发（逃生门 `AllowLegacyRdpSession`），存在**行为分裂**风险：同一套产物，有人配置出多会话、有人是共享模式，两者数据模型完全不同，Bug 修复和验收都无法统一。
2. 大量死代码长期占用维护注意力，且增加攻击面（多会话路径的 RDPWrap 安装、账户创建、3389 开放等高风险操作仍隐藏在代码里）。
3. 维护者/新人无法判断"到底以哪个架构为准"。

**优化建议**

1. **建立"架构唯一真源"**：以 `docs/架构-单会话共享与双光标.md` 为权威架构文档，在 README 顶部显式声明"产品形态只有一种（共享模式）"。
2. **清理死代码**：删除 `RdpSessionManager.cs`、`SessionLauncher.cs` 中多会话专属逻辑；从 `AgentConfig` 移除 `UseRdpSession / WorkerUser / WorkerPassword / RdpLoopbackHost / AllowLegacyRdpSession` 字段；从 `install-agent.ps1` / `create-remote-user.ps1` 移除 `-MultiSession` 分支。
3. **如确需保留逃生能力**，将其抽到独立 `Legacy` 子工程并明确标注"仅历史兼容、不参与验收"，避免与主路径混淆。
4. **代码中加编译期约束**：若完全放弃多会话，可用 `[Obsolete]` 标记或直接在配置反序列化后抛错（而非静默回写），让配置错误尽快暴露。

### P1-2 版本控制：完全没有版本控制

**问题概述**

`E:\Learn\MeProject\2026.9.20-uu` 与 `RemoteControl/` 均**无 `.git`、无 `.gitignore`**。

**详细说明**

- 项目已是一个**可交付的完整产品**（有安装包、授权体系、验收报告），但没有 git 仓库。
- 后果：
  1. **无法回滚**：任何一次错误改动都不可逆，只能靠人工记忆；
  2. **无法追溯**：`架构-单会话共享与双光标.md` 这类"客户反馈→定位→处置"记录，靠日期和手写，无法与代码 diff 对应；
  3. **无法隔离构建产物**：因为无 `.gitignore`，即使初始化 git，3.5GB 的 bin/obj 也会被误提交。

**优化建议**

1. **初始化 git 仓库**（`RemoteControl/` 作为仓库根），并提交初始基线。
2. **写 `.gitignore`**，至少排除：
   ```gitignore
   **/bin/
   **/obj/
   **/toolsnuget-packages/
   *.user
   *.suo
   build/
   server/
   setup-agent/
   tests/e2e-run/
   tests/e2e-verify/
   pyrev/
   *.log
   ```
   （`build/` 属分发产物，建议只保留清单或 CI 重新生成；`server/`、`setup-agent/` 是产物目录，应交给构建脚本，不提交。）
3. **敏感文件不入库**：`服务器.txt`（含密码）**严禁提交**，密钥/私钥同理。
4. 养成"重要改版前先 commit"的习惯（与你在其他项目里的做法一致）。

### P1-3 安全：服务器明文凭据外泄

**问题概述**

`E:\Learn\MeProject\2026.9.20-uu\服务器.txt` 明文记录了香港服务器（`202.60.232.209`，root）的**密码（已脱敏，见密码管理器）**，且该 IP 硬编码进多个源文件。

**详细说明**

- 该文件位于项目根目录，任何拿到项目（或 git 后误提交）的人都能直接 SSH root 进服务器。
- 同一 IP `202.60.232.209` 被硬编码在：
  - `src/Tools/AgentSetup/Installer.cs:77`
  - `src/Tools/AgentSetup/SetupSettings.cs:30`
  - `src/Tools/AgentSetup/SilentRunner.cs:64`
  - `src/Tests/Agent.Common.Tests/RelayLicenseProbeTests.cs:24`
- 这意味着**分发给客户的安装包内置了公网中继服务器地址**（明文、写死、无法通过配置覆盖的部分）。

**为什么是问题**

1. root 密码泄露 = 服务器完全失守，且该服务器承载所有被控端的中继流量与文件暂存（可被用于横向攻击被控端）。
2. 安装包硬编码服务器 IP，客户换服务器/域名时必须重新编译分发，且明文 IP 易被中间人篡改指向恶意服务器（配合 ws:// 明文，可被劫持）。

**优化建议（紧急）**

1. **立即修改该服务器 root 密码**，并检查是否有异常登录记录。
2. **删除或脱敏 `服务器.txt`**：改为只保留 IP + 提示"密码存于密码管理器"，绝不落盘明文。
3. **服务器地址改为配置/环境变量注入**：安装包默认读 `setup-defaults.ini`，不写死 IP；部署时用域名而非裸 IP。
4. **启用 TLS（wss://）**：见 P1-4。

### P1-4 安全：中继链路默认明文 + 无鉴权测试默认

**问题概述**

中继链路默认走 `ws://`（明文），且测试模式允许**无令牌**连接。

**详细说明**

- 客户端默认地址 `AppConfig.cs` 为 `ws://127.0.0.1:8080/ws`（本地开发没问题），但公网部署文档提示默认"无鉴权测试"。
- `README.md` 自己警告："公网必须启用令牌，否则任何人猜到被控端 ID 就能连上被控端"。
- 安装包硬编码的公网地址是 `ws://202.60.232.209:8080/ws`（明文、无 TLS）。

**优化建议**

1. **公网强制 wss://**：中继服务器用 nginx/证书终止 TLS，客户端默认地址改为 `wss://`。
2. **默认启用鉴权**：把"无令牌"模式从默认改为显式开关，出厂默认必须带 token。
3. 安装包分发时通过 `setup-defaults.ini` 注入 `wss://域名` 和 token，避免明文 IP + 明文传输。
4. 建议加 HTTPS 跳转：`ws` 请求 301 到 `wss`。

### P2-5 目录治理：src 目录被构建产物严重污染

**问题概述**

`src/` 目录高达 **3.47 GB**，其中绝大多数是构建产物而非源码。

**详细说明**

- 每个子工程（Agent.Common、Coordinator、Worker、Viewer、各 Tools、Tests）内部都带着 **`bin/`、`obj/`、`toolsnuget-packages/`**（NuGet 包缓存）。
- 重复最严重的是：
  - `microsoft.windowsdesktop.app.runtime.win-x64.8.0.31.nupkg`（35 MB）× **至少 6 份**（每个子项目一份）；
  - `microsoft.netcore.app.runtime.win-x64.8.0.31.nupkg`（34.5 MB）× 至少 6 份；
  - `Microsoft.Windows.SDK.NET.dll`（23.7 MB）× **超过 10 份**（每个子项目的 bin/Release/Debug + toolsnuget-packages）。
- 还有大量 `*_wpftmp.csproj.nuget.*` 临时构建残留（Viewer/obj 里 6 份）。
- `src/Tools/AgentSetup/obj/.../被控端安装程序.dll`（126.7 MB）× 2 份（bin+obj）。

**为什么是问题**

1. **空间浪费**：仅 SDK DLL + nupkg 的重复就占约 500 MB+。
2. **易误提交**：无 .gitignore 时，这些产物若入库会让仓库爆炸。
3. **构建脆弱**：缓存散落在每个子项目，NuGet 恢复/清理逻辑混乱，容易"改了不生效"。

**优化建议**

1. **清理**：删除所有 `**/bin`、`**/obj`、`**/toolsnuget-packages`。NuGet 缓存应统一走全局缓存（`%USERPROFILE%\.nuget\packages`），不该复制进项目。
2. **统一输出**：在解决方案根加 `Directory.Build.props`，把所有工程的 `BaseOutputPath`/`BaseIntermediateOutputPath` 指到项目外的单一 `artifacts/` 目录，避免每个子项目各自堆积。
3. **写 `.gitignore`** 排除这些目录（见 P1-2）。
4. 排查为何 `toolsnuget-packages` 会出现在源码里——很可能是离线/单文件发布时人为把包缓存拷进了项目，应改为 NuGet 全局缓存。

### P2-6 冗余：构建产物多份重复

**问题概述**

同一组产物在 `src/**/bin`、顶层 `build/`、顶层 `server/`、`setup-agent/`、`tests/`、`tools/`、`viewer/` 等多个位置重复存放。

**详细说明**

- **被控端安装程序**存在两个版本：
  - `build/setup-agent/被控端安装程序.exe`（201 MB）
  - `build/setup-agent/远程控制被控端-安装程序.exe`（83 MB）
- **分发 zip 重复**：
  - `build/payload.zip`（126.6 MB）
  - `build/被控端安装包.zip`（194.2 MB）
  - `build/主控端安装包.zip`（97.1 MB）
- **中继服务器二进制**：
  - `build/server/` 下 4 个（linux-amd64/arm64/windows-amd64/rcserver.exe）
  - 顶层 `server/` 下还有 `rcserver-windows-amd64.exe`、`rcserver.exe`（7.3 MB ×2）

4. 对 payload.zip / 安装包做一次内容比对，去重。

### P2-8 职责划分：目录职责重叠

**问题概述**

多个顶层目录职责重叠，同一类产物散落多处，难以判断"哪个是正式交付物"。

**详细说明**

- **可执行文件散落**：
  - 中继服务器：`build/server/`（4 个）+ 顶层 `server/`（2 个）+ `src/Server/rcserver.exe`（1 个）= 7 份；
  - 被控端程序：`build/agent/` + `src/**/bin/` + `setup-agent/` + `参考/DB/` 多处；

- **文档散落**：`docs/使用说明.md`、`build/agent/docs/使用说明.md`、`build/viewer/docs/使用说明.md` 三份同名文件，内容是否同步存疑。
- **drivers/ 与 build/ 下重复**：`drivers/VirtualDisplayDriver/`、`drivers/RDPWrap/` 与 `build/agent/drivers/` 下的驱动重复存放。

**优化建议**

1. 建立清晰的顶层结构，职责单一：
   ```
   RemoteControl/
   ├── src/        # 仅源码（.cs/.go/.xaml/.csproj）
   ├── scripts/    # 构建/部署/安装脚本
   ├── docs/       # 唯一文档源（Markdown）
   ├── drivers/    # 第三方驱动原始包（版本化、只读）
   ├── build/      # 唯一构建产物目录（可删除，由脚本重建）
   ├── third_party/# 依赖（ffmpeg 等）
   ├── tests/      # 测试源码（并入 src 或独立）
   └── 参考/       # 竞品逆向，移到仓库外或 docs 外
   ```
2. `使用说明.md` 只保留一份源，构建时拷贝进产物。
3. 顶层 `server/`、`setup-agent/`、`tests/`、`tools/`、`viewer/`（可执行 + 编译产物）全部收敛到 `build/` 对应子目录。

## 四、授权体系专项评估（相对健康的部分）

`src/Agent/Agent.Common/LicenseGate.cs` 与 `LicenseCodec.cs` 的授权设计**值得肯定**：

- **签名算法**：ECDSA P-256 + SHA-256（r‖s 32 字节，IEEE P1363），私钥只在厂商上位机（`LicenseKeygen`），中继与客户端只内置公钥 → 反编译交付物无法伪造激活码，对抗 AI 破解的关键设计正确。
- **防绕过**：被控端本地二次验签 + 磁盘缓存 + 到期硬停机 + 时间回拨检测 + 防"屏蔽中继走 P2P 白嫖"。
- **Server 侧**：license.go / revoke.go / admin 令牌分层。

**但仍需注意的短板**：

| 短板 | 说明 | 建议 |
|------|------|------|
| 厂商工具即单点 | `LicenseKeygen` 是离线签名工具，一旦泄露即可签发任意激活码 | 厂商工具与私钥**隔离存储、离线使用**，绝不进版本库/交付物 |
| 中继 token 随包分发 | `-token` 会进客户安装包，`admin-token` 若复用则 admin 接口失守 | 强制 admin-token 与 relay-token 不同（代码已校验，需在部署文档强调） |
| 无吊销联动 | 本地缓存激活码无在线吊销检查（离线可一直用到到期） | 若接受离线场景则保留；若需更强的"随时吊销"需加在线状态上报 |
