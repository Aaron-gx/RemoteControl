# 单会话共享 + 双光标：架构定稿与被控端修复说明

> 2026-09-22。本文回答客户提出的四件事：**副屏必须共享管理员账户的数据（不是新建账户）**、
> **打开应用后黑屏卡死**、**CV（剪贴板/文件传输）必须可用**、**主屏用户不能看见副屏鼠标且要完整鼠标操作**，
> 并记录开源方案调研结论与本机（开发机）只做主控端的约定。

---

## 0. 一句话结论

产品形态**只有一种**：

> 被控端在**管理员已经登录的那个账户**里，额外挂一块**虚拟外屏**；远端在这块屏上干活，
> 本机用户在自己的物理屏上干活。两边是**同一个账户、同一份 profile、同一个微信实例** ——
> 微信窗口能从物理屏拖到外屏、也能拖回来。

"新建 `RemoteWorker` 用户 + RDP 回环会话"这条路已经**在代码和安装脚本两个层面封死**。

**光标**：本机用户永远独占真实系统光标、永不被打断；远端默认也是原生光标，只有在本机用户正在用机器的
那段时间里自动降级为"后台定向注入"（不碰系统光标，事件直接投给窗口）。远端光标由主控端自绘，
被控机上不存在任何可见的远端光标。实现见 §2.3～§2.5，实测证据见 §2.5。

## 2. 光标：为什么"两只完全独立的鼠标"在单会话里做不到

### 2.1 硬限制（先把话说透）

一个 Windows **交互会话（session）只有一个系统光标**，也只有一个**前台窗口**。
Win32 应用之所以能"点到"，是内核按**当前光标位置**做命中测试后派发 `WM_LBUTTONDOWN` 等消息的。
推论：

- 想让**任意第三方应用（微信、浏览器、模拟器）**都获得**完整鼠标操作**（悬停高亮、工具提示、
  拖拽、右键菜单、滚轮、拖放），就必须让**真实的系统光标**处在那个位置上 —— 没有别的路；
- 而"两个用户各有一只互相看不见的光标"要求系统支持**多指针**。Windows 桌面版**不提供**这个能力
  （`InjectSyntheticPointerInput` 只接受 `PT_PEN`/`PT_TOUCH`，非主指针不会升级成旧式鼠标消息，
  普通 Win32 应用收不到；`EnableMouseInPointer` 是会话级全局开关且需重启）。

所以"**互不可见 + 完整鼠标操作 + 同一个桌面**"三者**不可能同时由操作系统直接满足**，
必须选一个折中。我们的选择见 2.3。

### 2.2 三个方案对比

| | A. 远端独占系统光标在虚拟屏（**已实现**） | B. 拦截物理设备 + 自绘光标（MouseMux 路线） | C. 后台消息注入（不碰光标） |
|---|---|---|---|
| 原理 | 远端输入 `SetCursorPos`(外屏坐标)+`SendInput`，光标始终在**没有物理输出**的外屏上；本机物理输入一到就把光标"还"回物理屏 | 用过滤驱动把物理鼠标从系统输入栈摘出来，本机光标由自己的覆盖层绘制，系统光标永远留给远端 | `PostMessage` 直接往目标窗口送 `WM_MOUSEMOVE/WM_LBUTTONDOWN`，光标一动不动 |
| 完整鼠标操作 | ✅ 100% 原生（悬停/拖拽/右键菜单/滚轮/拖放/工具提示） | ✅ 原生（远端）+ 本机需自绘（形状/悬停要自己实现） | ❌ 悬停/拖拽/菜单跟踪/`GetCursorPos`/游戏与 Electron 类应用大量失效 |
| 本机看不见远端光标 | ✅ 外屏没有物理输出，天然看不见 | ✅ | ✅ |
| 本机用户无感 | ⚠ 基本无感；**两边同时动**时光标会跟最后一个动的人（见 2.3 边界） | ✅ 完全并行 | ✅ |
| 需要内核驱动 | 不需要 | **需要**（`Interception` 在 Win11 上要 testsigning，且证书已被 EA 反作弊拉黑；`vmulti` 驱动未签名） | 不需要 |
| 失败时的后果 | 钩子挂了 → 本机一切照旧 | 覆盖层挂了 → **本机用户没有光标** | 应用不响应，用户以为"鼠标坏了" |
| 工程量 | 已完成 | 2~4 周（含驱动签名、光标形状/悬停自绘） | 小，但兼容性不可接受 |

**结论：采用 A，并在 A 之上加了"后台定向注入"作为共存路径（§2.5 已实现）。** B 作为阶段二保留（§2.6），
C 只在个别应用上做补充手段。

### 2.3 已实现的方案 A（`CursorArbiter`）

代码：`src/Agent/Agent.Worker/CursorArbiter.cs`，接线在 `Agent.Worker/Program.cs`。

- 远端输入原本就带 `MOUSEEVENTF_ABSOLUTE|MOUSEEVENTF_VIRTUALDESK`，并且**按键/滚轮前先发一次 MOVE**
  （`InputInjector`），所以远端每一次操作都保证光标先落到外屏上的正确像素。
- 新增 `WH_MOUSE_LL` 钩子，**只认自己注入的事件**（`InputInjector` 现在给所有注入事件打了
  `dwExtraInfo = 'RWCTRL01'` 记号 —— 只靠 `LLMHF_INJECTED` 分不清"远端注入"和"触摸板/厂商驱动用
  SendInput 送的输入"，两者待遇正好相反，所以必须打记号）。
- 判定规则（只在采集目标**是虚拟屏**时启用）：
  - 事件是我们注入的 → 原样放行，只记录位置；
  - 物理事件、且光标**不在**外屏上 → 原样放行，零开销、零行为变化；
  - 物理事件、且光标**还停在外屏上**（远端刚用过）→ `SetCursorPos` 把光标还回本机用户上次在物理屏的
    位置（并按本次物理位移补偿一下），然后**把本次按键/滚轮按归还后的坐标重放**（重放事件不带
    `ABSOLUTE`，落点就是刚设好的那个像素，无取整误差），原事件吃掉。
    → **本机用户永远看不见远端光标，点击也永远落在自己的屏上**（否则那一击会打到外屏上他看不见的远端窗口）。
- 顺带接了一个键盘钩子，**只用来判断"本机用户是不是正在用键盘"，从不拦截按键**。
- 失败安全：钩子装不上/钩子内抛异常 → 记一条日志，完全不介入；进程退出自动 `Unhook`。

**边界（写在明处）**：

1. 外屏必须开着（`EnableVirtualDisplay=true`）。若被关掉，远端只能在物理主屏上工作，那时仲裁会反过来
   打断远端，所以**那种配置下不启用仲裁**（`Program.cs` 会打警告）。
2. 两边**同时**操作鼠标时，光标位置是"单例"，谁最后动谁占；本机用户的表现是"光标回到我上次的位置"，
   远端下一次输入会立刻把光标拿回外屏。这是单会话方案的物理上限，不是 bug。
3. **键盘焦点同样是单例**：远端敲的键进的是**当前前台窗口**。所以新增了两道保护：
   - 打开应用时**不再无条件抢前台**（本机用户最近 2.5s 内动过键鼠就跳过，远端点一下窗口即可自行激活）；
   - 本机用户最近 800ms 内动过键鼠时，**远端按键先丢弃**，并限流提示主控端原因
     （宁可远端"暂时打不了字"，也不能把字打进本机用户正在编辑的文档）。
4. 安全桌面（UAC 提权框、锁屏、Ctrl+Alt+Del）里采集与注入都进不去 —— 这是 Windows 的设计，
   主控端会明确提示原因。

### 2.4 远端光标怎么显示：改由主控端自绘

采集端**不再把系统光标烤进画面**（`WgcFrameSource` 关掉 `IsCursorCaptureEnabled`，GDI 兜底路径也删掉了画光标的代码），
远端光标改由**主控端自绘**：`RemoteScreenControl` 在自己的 OnRender 里按"我们最后发给被控端的那个画面坐标"
画一个矢量箭头。

这样处理有两个好处：

1. **被控机上从来没有出现过任何可见的远端光标** —— 本机用户在任何模式下都看不见它（不是靠"藏"，是那里根本没有）；
2. **远端永远看得见自己的指针** —— 尤其是后台定向注入模式下，系统光标压根不在外屏上，靠烤进画面的老做法
   会看到"光标消失"。

### 2.5 双光标（已实现）：本机用户独占真实光标，远端走后台定向注入

这是对 §2.3 的升级。§2.3 里本机用户和远端是**分时抢同一个系统光标**（本机用户一动就"归还"）。
现在再加一条路：**干脆不去碰那个光标**。

**设计**（代码：`Agent.Common/BackgroundInput.cs` + `Agent.Worker/MouseRouter.cs`）

- **本机用户空闲**（默认 1.2 秒内没动键鼠）→ 远端走 **真实光标**：把光标摆到虚拟外屏的坐标上再 `SendInput`。
  悬停、拖拽、原生右键菜单、滚轮、拖放全是 100% 原生；而外屏没有物理输出，本机用户看不见这只光标。
- **本机用户一动手** → 远端**自动切到后台定向注入**：算准"那个位置下面是哪个窗口"
  （`WindowFromPoint` + `RealChildWindowFromPoint` 逐层下钻），把 `WM_MOUSEMOVE` / `WM_LBUTTONDOWN` / …
  **直接 Post 给那个窗口**，**系统光标一根毫毛都不动**。本机用户于是始终独占真实光标，永不被打断。
- **按住左键期间的整段拖拽会锁死路径**，不会中途切换把拖拽弄断；按住期间的移动一律发给"按下的那个窗口"
  （模拟 `SetCapture`）。
- **认领**：远端点过的窗口会被记下来，之后远端打字前先把该窗口带前台（本机用户在忙则直接跳过这次按键，
  见 §2.3 边界 3）—— 否则键会打进本机用户的前台窗口。

**实测结论**（探针 `src/Tests/BgInputProbe`，2026-09-22 六项全过，
原始输出见 `docs/evidence/双光标-后台注入探针-20260922.txt`）

```
[PASS] HitTest 命中按钮自身（期望 hwnd=0x1305E4，实得 0x1305E4）
[PASS] 投递 WM_MOUSEMOVE/LBUTTONDOWN/LBUTTONUP
[PASS] 后台注入点击按钮（目标窗口非前台）：按钮 Click 触发 1 次（期望 1）
[PASS] HitTest 命中文本框自身
[PASS] 投递点击+WM_CHAR
[PASS] 后台注入输入字符：文本框内容 = "A"
==> 探针结论：后台定向注入对标准控件可用
```

关键点：这是在**目标窗口不是前台窗口**的前提下测出来的，而且全程没有调用 `SetCursorPos`/`SendInput` ——
即"不碰系统光标也能点到别人窗口里的按钮"这件事，是**实测成立**的，不是纸上推演。

**和 MouseMux 比**：MouseMux 默认的 Switched 模式是"同一时刻只允许一个人按下去"（其他人被短暂挡住），
并发只对"听话的程序"生效。我们的设计里**本机用户从来不会被挡住**（他永远独占真实光标、永远原生），
被降级的是远端 —— 这正是"主屏不受影响"这条需求要的方向。

**已知边界**（后台注入拿不到的东西，本质都是"合成消息不是可信输入"）：

| 场景 | 能不能用后台注入 | 说明 |
|---|---|---|
| 标准控件（按钮/编辑框/列表/菜单条） | ✅ 实测通过 | 见上面的探针 |
| DuiLib 这类自绘 UI（微信就是） | ✅ 大概率可用 | 它自己在 `WM_MOUSEMOVE` 里做命中测试和悬停自绘 |
| Chromium/Electron（单 HWND） | ✅ 大概率可用 | 顶层窗口过程处理鼠标消息 |
| 原生 `TrackPopupMenu` 右键菜单 | ❌ | 要求窗口在前台、且要真实输入才能跟踪菜单 |
| 依赖 `SetCapture` 的拖拽 | ⚠ 多数可用 | 我们只能"模拟"（按住期间持续投递带 `MK_LBUTTON` 的移动） |
| DirectInput / 原始输入的游戏 | ❌ | 根本不走消息 |
| 区分"合成 vs 可信输入"的程序 | ❌ | 属于对方主动防御 |

以上拿不到的场景，在**本机用户停手 1.2 秒后会自动恢复真实光标**，能力当即可用 —— 也就是
"两边同时用"的代价只落在那段重叠时间里，且只落在远端身上。

**键盘**目前不做后台注入：本机用户空闲 → 真实注入（并先把认领窗口带前台）；本机用户在忙 → 丢掉这次按键
并提示主控端（§2.3 边界 3）。"非前台窗口后台打字"需要把 vk 翻译成字符（`ToUnicodeEx`）+ 自己维护修饰键状态，
是下一步，不是本轮。

**怎么自己验**（会闪两个属于探针自己的小窗口，约 1 秒；它不碰桌面上任何其它程序）：

```bash
DOTNET_ROOT=E:/tools/dotnet \
  RemoteControl/src/Tests/BgInputProbe/bin/Release/net8.0-windows10.0.19041.0/BgInputProbe.exe
```

### 2.6 如果还要更进一步：内核驱动级的真并行

只有一条路：把物理鼠标从系统输入栈里摘出来（内核过滤驱动），本机光标改由自己的覆盖层（Layered Window /
DirectComposition 顶层穿透窗）绘制，系统光标**独占留给远端**。届时两边才能真正同时、互不可见地操作。
代价与风险见 §2.2 B 列 —— 需要驱动签名（客户机器上装内核驱动 + Win11 的 testsigning 限制 + 反作弊拉黑），
以及自绘光标要补齐形状、悬停、提示等细节。**建议在主方案（A）跑稳、且确实出现大量"两边同时用"的场景后再做。**

## 3. 开源调研结论（GitHub）

**没有**任何开源项目直接等于"单会话 + 双独立光标 + 完整鼠标操作"。可复用的积木与最接近的产品：

| 项目 / 产品 | 是什么 | 对我们的价值 |
|---|---|---|
| [MouseMux](https://www.mousemux.com/pages/releases/) | 商业闭源。单会话多光标，多路复用模式，号称"emulates part of the input layer of Windows"，用 Layered Window/DirectComposition 画虚拟光标，且支持 TeamViewer/RustDesk 这类被采集的画面 | **证明方案 B 可行**，也是我们要对标的形态；闭源，不能直接用 |
| [DuoStream/Duo](https://github.com/DuoStream/Duo) | 开源多座位（TermWrap+Sunshine+Moonlight），给每个用户**各自独立的桌面** | 参考其虚拟屏与会话管理；但**独立桌面 = 数据不共享**，不满足我们的产品本意 |
| [neo0oen619/neo_multiseat](https://github.com/neo0oen619/neo_multiseat) | 开源 RDP 多座位脚本（3~10 座） | 同上：RDP = 独立会话 = 不共享 |
| [itsmikethetech/Virtual-Display-Driver](https://github.com/itsmikethetech/Virtual-Display-Driver) | 虚拟显示器驱动（我们已在用 MttVDD） | 现状依赖 |
| [oblitum/Interception](https://github.com/oblitum/Interception) | 键盘/鼠标**过滤驱动**，可摘设备、可注入 | 方案 B 的驱动基座；**Win11 上安装问题多**（需 testsigning、被杀软隔离、证书被 EA 反作弊拉黑），不能作为商业产品依赖 |
| [djpnewton/vmulti](https://github.com/djpnewton/vmulti)、[nefarius/vmulti](https://github.com/nefarius/vmulti)、[xaviersykora/vmulti-win11](https://github.com/xaviersykora/vmulti-win11) | 虚拟 HID 多点设备驱动（多鼠标/多点触控），可在**不移动系统光标**的情况下模拟额外鼠标 | 方案 B 的另一个基座；驱动未签名 |
| [evilC/AutoHotInterception](https://github.com/evilC/AutoHotInterception) | AHK 的设备级输入拦截库 | 原型验证用 |
| [trycua/cua](https://github.com/trycua/cua)（cua-driver-rs v0.5.2） | 开源 Computer-Use Agent 驱动，Windows 上明确做了"**不抢焦点的后台输入** + 多光标 demo" | 方案 C 与"后台输入"的最新实践参考 |

结论：**方案 A 自己实现（已完成）；方案 B 需要自研 + 承担驱动签名风险。** 另外 ASTER / IBIK 这类商用多座位
软件用的是"多会话"，同样不共享一个桌面，不满足"微信拖来拖去"这个验收标准。

## 4. 黑屏：三条已验证的代码级成因（全部已修）

| # | 成因 | 证据 | 修复 |
|---|---|---|---|
| 1 | **采集面失效后无声无息**。WGC 拿不到帧、又没有上一帧可顶时 `return false` 但 `error` 是**空字符串**，而上层只在 `error` 非空时才计数/记录/重建 → 黑屏且日志里**一个字都没有** | `WgcFrameSource.Capture` 原 `return false;` + `Program.cs` 的 `if (!string.IsNullOrEmpty(err))` | 该路径改为返回明确 error 并计数；新增采集项 `Closed` 事件订阅（显示器移除/重建时立刻置失效）；补一条"已 N 秒没有新画面"的限流告警，把"画面静止"和"采集已死"在日志上分开 |
| 2 | **编码器尺寸与采集尺寸脱钩**。ffmpeg 的 `-video_size` 是启动参数、运行期改不了；而采集器尺寸会随显示模式变（打开游戏/播放器改分辨率、外屏重建）→ 喂进去的帧被切碎/ffmpeg 立刻退出 → `RestartEncoder` 又用**同一个错尺寸**重建 → 无限重启、0 帧 | `WgcFrameSource.cs` 会改 `Width/Height`；`Program.cs` 的编码器在 `Start()` 里一次性固定尺寸 | 采集循环里比对 `_source.Width/Height` 与 `_encoder.Width/Height`，不一致就按新尺寸**重建编码器**并发 `StreamReset` |
| 3 | **硬件编码器死了没有退路**。nvenc/qsv/amf 被"打开的应用"抢占/复位 GPU 会话后一直启动失败，而探测结果被 `EncoderCache` **永久缓存**，于是每次重建都拿同一个坏编码器 | `FfmpegEncoder.ResolveEncoder` 的缓存 + `RestartEncoder` 无降级 | 新增 `ForceSoftware()`：连续 3 次重启失败即降级 `libx264`，并在 `ResolveEncoder` 里**先于缓存**生效 |

另外去掉了一处历史风险：`WindowManager.MoveToTargetIfNeeded` 原来对任何窗口都 `ShowWindow(SW_RESTORE)`
（对最大化的/全屏独占的应用会改掉它的显示状态，代码注释里就写着"用户反馈的打开应用后黑屏卡掉"），
现在**只在窗口确实最小化时**才 restore。

> 关于旧多会话方案：它的黑屏来源（mstsc 会话掉线/被最小化 → 无显示表面、安全桌面）随着这条路被封死一起消失。

### 4.1 另一类"没画面"：链路拥塞 + 自毁式重建码流（2026-09-22 修复）

现场：主控端连上后**软件列表、分辨率、延迟全都有，就是没有画面**，`FPS/码率` 一直显示 `--`。
用只读探针（`scripts/_probe_viewer.js`）以 viewer 身份连中继看被控端到底在发什么，真相是：

```
WorkerStatus {"CaptureFps":23,"EncodeFps":23,"Backend":"WGC","FramesSent":19112,
              "BytesSent":315962715,"DirectActive":false,"RelayChunks":6712}
DirectCandidates {"port":47890,"tcp":["192.168.1.20:47890"],"public":null,"relay":true}
主控端状态栏：延迟 2797ms
```

- 被控端**一直在正常采集与编码**（23fps、累计已发 316MB），没有毛病；
- 主控端也在正常收报文（状态上报、软件列表、分辨率都到了），但**始终凑不出一个完整的关键帧**；
- 根因链：**P2P 直连建不起来**（候选里 `public` 是 `null`，只给了内网地址 `192.168.1.20`，跨网必然失败）
  → 视频全部挤在一条延迟 2.8 秒的中继上 → 帧环写不进去 → 老代码的反应是
  **"丢掉这一块并重建码流"** → 重建会让主控端**重置解码器、重新等关键帧** → 慢链路上这个循环永不收敛，
  画面永远是黑的。

还有一个观测陷阱要点出来：主控端的 `FPS/码率` 是**在成功渲染出一帧之后才更新**的
（`OnRenderTick` 中 `_decoder == null` 或没取到帧就直接 `return`，`MainWindow.xaml.cs`），
所以这两个 `--` 的含义是"一帧都没解出来"，**不是**"一个字节都没收到"。

四处修复：

| 修法 | 说明 |
|---|---|
| **环满不再重建码流** | 只丢这一块并计数，交给自适应去降码率；环写超时从 800ms 收到 250ms，不再把"编码器→帧环"这条链子卡住那么久 |
| **GOP 收到 1 秒** | 主控端接入/被重置/丢块之后，最多 1 秒就能靠下一个关键帧自愈（原来是 2 秒） |
| **码率自适应**（`Agent.Worker/BitrateGovernor.cs`） | 拥塞就逐级降档（100% → 60% → 35% → 20% → 20%+降帧率 → 250k+半帧率），通畅 30 秒再逐级升回；**换档时不发 StreamReset**（分辨率没变、编码器带内重复 SPS/PPS，主控端不需要重置解码器——重置一次就要重新等关键帧，那正是要避免的） |
| **主控端把原因显示出来** | 状态栏新增 `被控端: 采集 23fps · 4000kbps/30fps · WGC · 已降档 N 级 · ⚠拥塞丢弃 N 块/s`；画面连续 3 秒出不来时，在**画面上**叠一条明确原因（网络拥塞 / 被控端采集过低 / 安全桌面 / 在等关键帧），不再让人对着黑屏猜 |

**部署结论（重要）**：P2P 直连不成功时视频只能挤中继。候选里 `public` 为空说明 UPnP 没映射成功，
需要在被控机 `agent.json` 填 `DirectLinkPublicAddress`（形如 `公网IP:47890`）或在路由器上做 47890 端口映射。

### 4.2 再往下挖一层：控制与视频混在一条队列里，把控制通道拖死了（2026-09-22 修复）

4.1 的修复部署后仍无画面，探针（`_probe_viewer.js`）拿到的新状态暴露了更深的三个问题：

```
BitrateKbps:4000 FrameRate:30 AdaptiveLevel:0 RingDropped:0
RelayQueued:1480→1489（还在涨）RelayDropped:0 RelayChunks:1095
CaptureFps:22.2 → 7.5        ← 采集被拖垮
frame counts : 0x01=2        ← 22 秒只收到 2 帧
主控端状态栏：延迟 19797ms      ← 心跳往返 19.8 秒
```

| 问题 | 机制 | 修法 |
|---|---|---|
| **① 控制与视频共用一条队列** | 协调器的发送队列是 **512 深 + DropOldest**，心跳/授权/剪贴板/视频全在里面。被控端上行只有一两百 kbps 而编码在 4Mbps → 队列瞬间被视频灌满 → **心跳回声被压在 20 秒的视频后面** → 主控端判定"服务器无响应"→ 反复断开重连（中继日志里一分钟连了 5 次，每次 1~20 秒，每个会话都活不到关键帧到达） | 拆成两条队列：**控制优先**、视频单独一条只留 ~1 秒且丢最旧的 |
| **② 丢弃数永远是 0，看着像没丢包** | `DroppedCount` 只统计 `TryWrite` 失败，而 `DropOldest` **永远不失败** —— 它在静默丢弃最旧的消息（包括控制消息） | 视频队列单独统计"写入时已满"的次数作为真实丢弃指标；控制队列满才计丢 |
| **③ 自适应的拥塞信号选错了** | Worker 只能看到帧环，而帧环会被协调器**慢慢抽干**（写 250ms 成功、不丢块）→ `RingDropped` 一直是 0 → 自适应一次都没降档，眼睁睁看着 4Mbps 压在 100kbps 的链路上 | 由协调器测"中继出口积压/挤掉帧"，每秒通过 IPC（`IpcBitrateHint`）告诉 Worker；自适应同时看这两个信号 |
| **④ WebSocket 自带保活把好连接误杀** | `ClientWebSocketOptions.KeepAliveInterval = 20s`，而 pong 宽限默认跟着它；弱网往返 19.8 秒 → 一到点客户端自己 `Abort()` | 关掉 WS 保活（`Timeout.InfiniteTimeSpan`），改由应用层心跳 + "整整 60 秒没有任何入站消息才重连"的看门狗 |
| **⑤ 档位不够低** | 原下限 250kbps，而现场上行只有 ~100kbps | 档位扩到 8 档，最低 **100kbps / 5fps**（画面很糊但能动，先保住"能操作"） |

**现场网络实测（这是真正的瓶颈，代码改不了它）**：

```
服务器 → 被控端(120.12.200.170) ping：20 发包 0 收到（100% 丢）
traceroute：到电信骨干 61.182.180.218 / 60.8.131.246 之后全是 no reply
ss -tni：rtt 112ms 正常，但 retrans 33 次、RTO 退避到 80 秒、65 秒收不到一个字节、连接死在 FIN-WAIT-1
按"软件列表 45KB 用了 6 秒"反推：被控端 → 香港 上行只有 60~100kbps
```

也就是说：**那台被控端的上行只有几十到一两百 kbps，任何视频方案都救不回来**。这次代码改动能让"控制通道不再被视频拖死、链路差时自动降到能承载的码率、主控端不再自己断开"，
但**画面能不能看，取决于链路**。要真正可用，只能二选一：
1. **修 P2P 直连**（绕开香港）：被控机做 47890 端口映射 + 填 `DirectLinkPublicAddress`；
2. **换中继位置**：给中国大陆的被控端配一个境外的优质线路或就近中继（`ServerUrlFallbacks` 已经支持多端点）。

### 4.3 让"切到 P2P"真正管用：被控端托盘开关 + 所有数据都走直连（2026-09-22）

现场暴露了两个缺口：

1. **被控端没有开关**：主控端一直有"链路（自动/仅中继/仅直连）"下拉，被控端托盘里却只有一个"退出" ——
   客户在机器前面既没法开关直连，也没法在路由器做完端口映射后把公网地址填进去（以前必须手改 `agent.json` 再重启）。
2. **只有视频走直连**：鼠标键盘、软件列表、状态上报、剪贴板全都挤在中继上。所以中继那条腿一坏
   （实测：机房侧把出站压到 15KB/s），"切到 P2P" 就只能救画面，操作和列表照样卡死。

改动：

| 位置 | 改动 |
|---|---|
| 被控端托盘 `TrayIcon.cs` | 右键菜单新增：`直连：<状态>`（打开菜单即刷新）、`启用直连（P2P）`（勾选即生效）、`复制直连地址`、`设置直连公网地址…`（弹输入框，保存后立刻重推候选）。托盘悬停显示 `服务器√ 直连：…` |
| 直连开关的实现 | 关 = `LicenseCheck` 里 `&& _cfg.DirectLinkEnabled` → 拒绝**新的**直连握手（监听保留，随时可开回来）；开 = 必要时现场 `Start()`。**都不用重启被控端** |
| 协调器 `SendToViewer()` | 所有"发给主控端"的消息统一"**直连优先、失败回退中继**"：视频、软件列表、状态上报、剪贴板通知、错误提示、流重置通知 |
| 主控端 `_direct.MessageReceived` | **修掉一个会致命的行为**：以前是 `if (msg.Type != VideoFrame) return;`，直连上的非视频消息**全被丢掉**。只改被控端不改这里，切到直连就会变成"画面有了、软件列表/状态栏/剪贴板全没了"，所以直连消息现在交给与中继**完全相同**的 `OnRemoteMessage` 处理 |

**仍然已知的缺口（下一步）**：主控端 → 被控端方向的**输入**（鼠标键盘）目前仍走中继回程。控制消息很小，
即使在 45% 丢包的链路上也能靠优先级队列挤过去（约几百毫秒），但要彻底"不受中继影响"，
还需要输入也走直连：主控端侧加一个发送队列（避免 UI 线程被 socket 写阻塞）+ 被控端侧加直连读取循环。
这一步等端口映射做好、能端到端验证时再上 —— 不验证不发货。

## 5. CV（剪贴板 / 文件）现状与缺口

**现状（已验收）**

- 文本剪贴板：**双向**，两端各挂 `AddClipboardFormatListener`，靠"剪贴板变化自动同步"＋去重/防回环。
- 文件：**只有"被控端 → 主控端"单向**。在被控端复制文件（`CF_HDROP`）即自动上传到中继
  （`/api/upload`，单文件上限 512 MiB、**10 分钟 TTL**），主控端在画面里按 Ctrl+V 下载。

**共享模式下要注意的一件事**：共享模式的剪贴板就是**本机用户的剪贴板**，所以本机用户复制的东西会被
自动同步给远端。同一个账户下这是预期行为，但**大文件自动上传**会吃被控端上行与服务器磁盘（且无确认）。

**缺口（建议下一步，本轮未动，避免破坏已验收路径）**

1. **主控端 → 被控端**的文件通道完全没有（`src/Viewer` 里没有任何上传代码；协议里的 `0x22 FileChunk`
   只有编解码和单测，是**没接线的死代码**）。要做成"双向"，需要：主控端拖拽/粘贴 → `/api/upload`
   → 新消息通知被控端 → Worker 下载到临时目录 → 写进本会话剪贴板（`CF_HDROP`）。
2. **主控端 Ctrl+V 的语义冲突**：当有远程文件待下载时，`MainWindow.xaml.cs` 会把 Ctrl+V 从"转发给远端"
   里**吞掉**，于是"往远端粘文本"和"取回远端文件"抢同一个按键。建议改成"收到文件通知时**立刻下载并在
   本地剪贴板就位**"，这样 Ctrl+V 就是普通的粘贴，不再需要吞键。
3. 文件传输的**开关与限额**：共享模式下建议增加"自动上传体积上限/确认"，避免误传大文件。

## 9. 2026-10-04 增补：消除"远程打开软件先在主屏闪一下"（客户反馈）

**现象**：主控端右键软件列表「打开」→ 新窗口先在**主屏**上出现，停 0.2~1 秒才被搬到副屏 ——
打扰正在主屏工作的本机用户。

**根因**（旧链路，`WindowManager.Open`）：

```
Process.Start(ShellExecute，无初始位置)
  → 新窗口按系统默认/程序自己的记忆位置开在**主屏**
  → EnsureWindowOnTarget 每 200ms 轮询（首次还要先睡 200ms）+ 周期 Sweep 每秒一轮
  → 找到窗口后才 SetWindowPos 搬去副屏
```

窗口在主屏的可见时长 ≈ 一到两个轮询周期（200ms~1s+），这就是客户看到的"闪一下"。
本质是"**先出生在主屏、事后搬家**"，搬得再快也只是把闪烁压短。

**修复：三层防线（`Agent.Worker/WindowManager.cs` + `Agent.Common/NativeApi.Launch.cs`）**

| 层 | 做法 | 覆盖 |
|---|---|---|
| ① 出生即外屏 | `CreateProcessW + STARTUPINFO(STARTF_USEPOSITION)`，初始窗口位置直接定在虚拟外屏。Windows 规则：程序 `CreateWindow` 用 `CW_USEDEFAULT` 定位时采用 STARTUPINFO 的 dwX/dwY —— 窗口**生下来就在外屏**，主屏根本不出现（零闪烁） | 绝大多数首次启动的程序 |
| ② 显示即捕获 | `SetWinEventHook(EVENT_OBJECT_SHOW)`（带外钩子，只在钩子线程泵消息时触发）：窗口**显示的那一刻**（第一帧画出来之前）就搬走，毫秒级。每次远程「打开」武装 25 秒，到期自动卸钩 | 自己定位/记住上次位置的程序（Chromium 系、微信…）、提权程序（回落 ShellExecute 后新 pid）、单实例程序（窗口交给同名老进程，按**进程名**认领） |
| ③ 轮询兜底 | 原 `EnsureWindowOnTarget`（200ms）与周期 `SweepNewWindowsFromPhysical`（1s）原样保留 | 一切漏网情况（控制台/conhost、Windows Terminal 宿主、慢启动） |

**安全边界（与既有闸门完全一致）**：

- 钩子回调里**本机用户正在动键鼠（`LocalActiveRecently`）→ 一个窗口都不碰** ——
  宁可那 25 秒里主屏多闪一下，也绝不抢走他正在开的程序；
- 只认"这次远程打开带出来的"窗口：① 刚启动的 pid；② 同名老进程（单实例）；③ 武装之后新出现的进程
  —— 三者都不是（本机用户自己的老程序弹了新窗口）→ 不动；
- 回调全部在专用钩子线程上触发，搬窗用已有的 `MoveToTargetCore`（不抢前台逻辑、`SW_RESTORE`
  只对最小化窗口调用等约束全部继承）；
- STARTUPINFO 只给**位置**（`STARTF_USEPOSITION`），不设尺寸 —— 程序默认大小照旧；
  提权程序（`ERROR_ELEVATION_REQUIRED`）与非 exe 自动回落 `ShellExecute` 老路径。

**日志特征**：修复生效时 `worker-*.log` 会出现
`已启动 xxx pid=N（初始位置=外屏）`（第①层命中）或
`新窗口刚显示就捕获（xxx，主屏 (x,y)）→ 即刻搬往外屏`（第②层命中）。

**本轮改动文件**：

| 文件 | 改动 |
|---|---|
| `src/Agent/Agent.Common/NativeApi.Launch.cs` | **新增**：`CreateProcessW`/`STARTUPINFO`、`SetWinEventHook`/`UnhookWinEvent`、钩子线程用的最小消息泵（`PeekMessage`/`MsgWaitForMultipleObjects`） |
| `src/Agent/Agent.Worker/WindowManager.cs` | `Open()` 改为"带外屏初始位置启动 → 回落 ShellExecute"；新增 `StartOnVirtualScreen` / `ArmShowCatcher` / `CatchLoop` / `OnWindowShown`（显示即捕获，含本机用户闸门与"是不是这次打开带出来的"三判据） |

**验收要点（在被控机上）**：主控端右键打开一个**从未运行过**的程序 → 本机主屏应**完全不出现**该窗口
（日志有"初始位置=外屏"）；打开一个**上次关在主屏**的程序（如微信）→ 主屏至多一帧不可察觉的闪烁
（日志有"刚显示就捕获"）；本机用户持续动鼠标期间远程打开 → 窗口留在主屏（不抢），本机用户停手后
由兜底轮询搬走 —— 这是"不打扰本机用户"闸门的预期行为。

**追修一（2026-10-04 深夜，v1.1.1）**：「此电脑」打开仍在主屏闪一下 —— explorer 是**常驻进程代开窗口**，
从打开到窗口 SHOW 只有 ~100ms，而旧实现"捕获期结束就卸钩、下次打开再装钩"要经过 500ms 空闲轮询 +
进程快照的延迟，**钩子还没装好窗口已经显示过了**（普通程序冷启动 300ms+ 躲得开，explorer 躲不开）。
修复两刀：① **钩子常驻**（装一次不卸，未武装时回调按捕获期判定、零动作，彻底消灭装钩竞态）；
② **武装期 60ms 快扫**（FastCatchSweep：枚举窗口 + 与钩子同一套判据 TryCatchWindow，钩子万一漏网
也在 3~4 帧内抓到）。快扫额外用**基线快照**过滤（武装时现拍）：只碰"打开指令之后才出现的窗口"，
绝不把本机用户早已开着的同名程序窗口整窝端走。

**追修三（2026-10-05，v1.1.3，视频证据驱动）**：两条现场反馈 ——
1. **"右键打开此电脑还是要闪一下才过去"**：SHOW 再快也是"显示之后"搬 —— explorer 创建窗口时带着
   它记住的上次位置（主屏），第一帧已经画在主屏了。补上**CREATE 事件预定位**：窗口刚创建、
   还没显示时就挪到外屏（隐藏窗口的挪动屏幕上零表现，显示出来直接在副屏）→ 主屏**零动作**。
   只预定位"像主窗口"的（有标题栏、非工具窗），隐藏辅助窗一个不碰；程序若在显示时又自己摆位，
   SHOW 钩子/快扫再抓一次（退化为 1 帧，不会更糟）。钩子区间扩为 CREATE..SHOW 一次挂上。
2. **"此电脑打开后，主屏开任何软件都被传到副屏"**：v1.1.2 的"本机物理输入晚于远端输入才拒"
   被打穿 —— 远端用户看画面时鼠标一直在画面上移动，远端输入时间戳被持续刷新、几乎永远更新，
   比较先后毫无意义。改为**只看本机**：`LocalUserTouchedRecently(12s)` —— 本机用户 12 秒内动过
   任何键鼠（双击开程序后等窗口出来正落在这个窗口里）→ 一切搬窗路径（预定位/SHOW/快扫/按名兜底）
   一票否决，远端是否在动无关紧要。

**追修二（2026-10-05，v1.1.2）**：两条现场反馈 ——
1. **"有时候打开此电脑到不了副屏"**：Win11 资源管理器默认把新窗口**并成已有窗口里的标签页**；
   桌面上已有资源管理器窗口时，"此电脑"被塞进主屏那个旧窗口里，**没有新窗口出现**，
   钩子/快扫/轮询全部无处下手。修复：`OpenThisPC` 改用 `explorer /separate ::{此电脑}`，
   强制独立进程开独立窗口（新窗口还属于新起的 explorer 进程，认领判据更干净）。
2. **"打开此电脑之后，主屏打开软件会自己跳到副屏"**：捕获器武装 25 秒期间，本机用户双击开程序 ——
   双击到窗口显示隔几秒，"1.2 秒内还在动"的闸门已过期，而"武装后新出现的进程"认领规则把它
   当成远端的抢走了。修复：所有搬窗路径（钩子/快扫/按名兜底）加**"最近一次人为输入是谁"**判据
   （`LocalUserWasLastActor`：10 秒内本机物理输入晚于远端输入 → 一律不碰）——
   远端侧数据由 WorkerContext 的 `_lastRemoteInputTick` 注入，物理侧来自光标仲裁器的
   `LastPhysicalInputTick`（远端注入的事件带 RWCTRL01 标记，不会污染物理时间戳）。

## 10. 2026-10-04 增补：进程合并（Coordinator 吞并 Worker，多会话遗留彻底删除）

**动机**：`Coordinator + Worker` 双进程与"跨会话 Named Pipe + 共享内存"这一整套 IPC，
是给已废弃的 RDP 多会话方案建的。共享模式下两个进程本就跑在**同一个会话**里，
数据却要走"编码 → 共享内存 → IPC → 中继"的内部绕路：多两次拷贝、多一层延迟、
多一片失败面（历史上修过的"低完整性标签/Unicode 命名"坑全是它带来的）。
随着旧方案代码删除，这套墙和递条子的规矩一起拆掉。

**合并后的形态**：

```
旧：Agent.Coordinator.exe ──NamedPipe(指令)＋共享内存(帧)──> Agent.Worker.exe（独立进程）
新：Agent.Coordinator.exe
      ├─ 托盘/中继/直连/授权/软件列表/文件上传（主 STA 线程，消息循环 = 托盘）
      ├─ worker-engine 线程（专用 STA 线程 + 自己的消息循环）承载 WorkerContext：
      │    WGC 采集 · ffmpeg 编码 · 键鼠注入 · 光标仲裁 · 剪贴板 · 窗口管理
      └─ WorkerBridge（进程内通道，取代管道+共享内存）
```

**为什么引擎必须是一条"带消息循环的 STA 线程"**（WorkerHost.cs，不是随手 Task.Run）：
原 Worker 主线程同时承担三件事，缺一不可 —— ① 剪贴板（OLE）写入必须在 STA 线程
（ClipboardWatcher.Invoker 靠它 marshal）；② 低级键盘钩子（WH_KEYBOARD_LL）装在哪条线程、
回调就在哪条线程跑，这条线程必须泵消息且不能被长活儿占住；③ `ExitThread()` 只结束引擎线程，
托盘/中继不受影响 —— 语义等价于旧架构"Worker 进程退出、Coordinator 看护再拉起"。

**WorkerBridge 的保真细节**（对应旧实现逐点平移，不是重设计）：

| 旧（跨进程） | 新（进程内） |
|---|---|
| Named Pipe 双向 + 各自 2048 深队列 | 两条 Channel（同样 2048 + DropOldest）+ 各自**串行分发线程** —— 处理器天然串行、与旧管道读写线程模型一致 |
| 共享内存帧环（4MB、写超时 250ms 丢块计数、Reset 清残帧、FillRatio 诊断） | `FrameChannel`：同样的字节限容/超时丢弃/Reset/FillRatio 语义 |
| 管道断开 → 旧指令自然丢弃 | `MarkWorkerConnected` 时清掉积压指令（防过期键鼠/打开软件投给新引擎） |
| 心跳消息被 IpcServer 滤掉 | 分发线程同样滤掉 |
| WorkerReady/WorkerStatus/MonitorInfo/剪贴板/文件/错误 等消息 | 原样传递（协议零改动，主控端与服务器**完全无感**） |

**踩到的两个"线程身份"坑（已修）**：
1. `MessageType.Stop` 的处理器跑在桥的分发线程上，直接 `ExitThread()` 退不了引擎 STA 线程的消息循环
   （旧架构里它在 Worker 自己的主线程上）→ 改为 `PostThreadMessage(WM_QUIT)` 投回引擎线程；
2. 引擎重启后新的 WorkerContext 订阅桥事件，旧实例若不退订会继续收到消息、与新实例抢输入 →
   Dispose 里显式退订。

### 11.1 文件夹复制（原来只支持单文件）

链路：被控端复制**目录** → ClipboardWatcher（`File.Exists` 改为文件/目录都收，`FileDropInfo.IsFolder`）
→ 协调器 `FolderTransfer.PackFolder` 压成临时 zip（上限 512MB，与中继单文件限制一致）→ 上传 →
通知带 `IsFolder/FolderName` → 主控端自动下载 → `ExtractToUniqueDir` 解压（重名自动 "(2)"、zip-slip 由 .NET 防护）
→ **把解压出的目录**放进本机剪贴板（CF_HDROP 支持目录，Ctrl+V 直接粘出文件夹）。单测 `FolderTransferTests`。

### 11.2 软件列表置顶「此电脑」

主控端列表第一项固定为「此电脑」（`SoftwareListMarkers.ThisPc = "::this-pc"` 哨兵，图标程序内绘制；
右键只有「打开」——关闭/搬动需要 pid，explorer 常驻不能杀）。被控端收到哨兵 →
`WindowManager.OpenThisPC()`（explorer.exe + 此电脑 CLSID），窗口摆到外屏靠既有三层防线
（STARTUPINFO/SHOW 钩子/轮询）。**新增保护**：`IsShellWindow` 一票否决桌面/任务栏窗口
（Progman/WorkerW/Shell_TrayWnd/SHELLDLL_DefView/SysListView32）——它们同属 explorer 进程且尺寸"正常"，

## 12. 2026-10-05 增补：热更新（自动更新）体系

**动机**：被控端散在客户机器上，每次修复的最后一公里是"发安装包→客户装→重启"；2026-10-05 的真机联调证明远程热部署可行且高效（_rcp.py 六轮迭代），遂产品化。

**架构**（与授权体系同一信任模型：**私钥只在厂商上位机**，客户端/中继只内置公钥）：

```
LicenseKeygen「更新签名」页 ──(私钥签 RCU1 更新码 + 上传 zip + 存清单)──> 中继 <data>/updates/
中继：GET /api/update/manifest（RC_TOKEN；按 AgentId 哈希 × rolloutPercent 灰度）
      GET /api/update/file/{name}（RC_TOKEN；路径穿越防护）
      POST /admin/update/package|manifest（管理令牌；/admin/update 小页面）
被控端 Updater：启动+30s 与每 6h 查清单 → 验签(ECDSA P-256，同授权码密钥) → 比版本
      → 下载 zip → sha256+大小比对 → 等空闲(连续 5 分钟无主控端) 
      → 分离启动 PowerShell：停旧→备份 Agent.*.dll→解压→启新
      → 新版本 45s 内写"报平安"标记；90s 没等到 → 脚本自动回滚备份并启旧
主控端：连接时查清单 → 验签+比版本 → 状态栏"有新版本"链接（只提示不自动更）
```

**安全要点**：更新码(RCU1 前缀)与授权码(RC1)同密钥不同前缀互不通用；下载地址不在签名内但包哈希在（改地址拿不到对哈希的包）；服务器未配清单=404=客户端安静无事；哈希/大小双重比对；`AutoUpdateEnabled` 配置可关。**TLS 缓发说明**：签名已保证更新完整性（MITM 换包无效），TLS 保护的是视频/键鼠传输隐私——待服务器有域名后补（裸 IP 无法申请正规证书，自签证书的信任分发反而更复杂）。

## 13. 2026-10-05 深夜增补：绝对零闪 + 黄框取消 + 副屏记忆位置回主屏 + 热更新真机闭环

### 13.1 绝对零闪（客户要求"一帧都不行"）

**帧级验证方法论**：`_rcp.py frames` 模式 → 切主屏采集 → 录 10 秒 H.264 → 本地 ffmpeg 抽帧 → 逐帧像素比对。
198 帧、阈值 80000 以上**零变化帧**（帧间最大差异 70516 = 鼠标光标级别，窗口出现会是百万级）。

三层防线（v1.2.5）：

| 层 | 机制 | 效果 |
|---|---|---|
| ① CREATE 预定位 | WinEvent CREATE → SetWindowPos 到外屏（窗口还没显示） | 主窗口直接出生在副屏 |
| ② 3ms 热旋转 | 打开后 2 秒内每 3ms 专用线程全窗口扫描（独立于异步 WinEvent） | 保证在 DWM 16.7ms 帧边界之前发现并 cloak |
| ③ DWM cloak | `DwmSetWindowAttribute(DWMWA_CLOAK)` 合成器层面当帧隐身 → 搬 → 恢复 | ①②都漏掉时的最后防线 |

关键认知：DWM 帧边界 16.7ms（60Hz），3ms 检测 + cloak **肯定跑赢第一个合成周期** → 窗口物理上不可能出现在主屏。

v1.2.1~1.2.4 的追修链（EVENT_OBJECT_CREATE=0x8000 常量错误 → 钩子常驻 → /separate → 分级闸门 → justOpened 4s 豁免 → 尺寸护栏 → cloak → 3ms 旋转）见 §9 追修一~四。

### 13.2 黄框取消

根因：WGC 对物理屏采集默认画系统"正在被捕获"指示框（`IsBorderRequired` 默认 true）——**不是 Viewer 画的**（Viewer 端黄框代码 9 月已删）。
修复：`WgcFrameSource` 会话加 `IsBorderRequired=false`。TFM 全线 19041→22000（该 API 需 20348 投影）。

### 13.3 副屏记忆位置回主屏（反向抓取）

Windows 记住程序**上次关闭时所在的屏**——副屏关过的软件，本机用户下次从主屏打开就直接"出生在副屏"（他看不见副屏）。
新增 `ReversePullToPrimaryIfLocalUser`：常驻 SHOW 监听 → 新窗口整块落在外屏 + 15 秒内只有本机物理输入 + 不在远端武装期 → 搬回主屏。

### 13.4 热更新真机闭环

1.2.1 → 1.2.2 全自主走通（检查→验签→下载→空闲→应用→报平安），期间机器被关机属巧合，重启后 1.2.2 正常。
