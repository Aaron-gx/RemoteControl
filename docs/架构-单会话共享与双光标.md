# 单会话共享 + 双光标：架构定稿与被控端修复说明

> 2026-09-22。本文回答客户提出的四件事：**副屏必须共享管理员账户的数据（不是新建账户）**、
> **打开应用后黑屏卡死**、**CV（剪贴板/文件传输）必须可用**、**主屏用户不能看见副屏鼠标且要完整鼠标操作**，
> 并记录开源方案调研结论与本机（开发机）只做主控端的约定。

---

## 0. 一句话结论

产品形态**只有一种**：

> 被控端在**管理员已经登录的那个账户**里，额外挂一块**虚拟外屏**；远端在这块屏上干活，
> 本机用户在自己的物理屏上干活。两边是**同一个账户、同一份 profile、同一个微信实例** ——
> 微信窗口能从物理屏拖到外屏、也能拖回来。

"新建 `RemoteWorker` 用户 + RDP 回环会话"这条路已经**在代码和安装脚本两个层面封死**。

**光标**：本机用户永远独占真实系统光标、永不被打断；远端默认也是原生光标，只有在本机用户正在用机器的
那段时间里自动降级为"后台定向注入"（不碰系统光标，事件直接投给窗口）。远端光标由主控端自绘，
被控机上不存在任何可见的远端光标。实现见 §2.3～§2.5，实测证据见 §2.5。

## 2. 光标：为什么"两只完全独立的鼠标"在单会话里做不到

### 2.1 硬限制（先把话说透）

一个 Windows **交互会话（session）只有一个系统光标**，也只有一个**前台窗口**。
Win32 应用之所以能"点到"，是内核按**当前光标位置**做命中测试后派发 `WM_LBUTTONDOWN` 等消息的。
推论：

- 想让**任意第三方应用（微信、浏览器、模拟器）**都获得**完整鼠标操作**（悬停高亮、工具提示、
  拖拽、右键菜单、滚轮、拖放），就必须让**真实的系统光标**处在那个位置上 —— 没有别的路；
- 而"两个用户各有一只互相看不见的光标"要求系统支持**多指针**。Windows 桌面版**不提供**这个能力
  （`InjectSyntheticPointerInput` 只接受 `PT_PEN`/`PT_TOUCH`，非主指针不会升级成旧式鼠标消息，
  普通 Win32 应用收不到；`EnableMouseInPointer` 是会话级全局开关且需重启）。

所以"**互不可见 + 完整鼠标操作 + 同一个桌面**"三者**不可能同时由操作系统直接满足**，
必须选一个折中。我们的选择见 2.3。

### 2.2 三个方案对比

| | A. 远端独占系统光标在虚拟屏（**已实现**） | B. 拦截物理设备 + 自绘光标（MouseMux 路线） | C. 后台消息注入（不碰光标） |
|---|---|---|---|
| 原理 | 远端输入 `SetCursorPos`(外屏坐标)+`SendInput`，光标始终在**没有物理输出**的外屏上；本机物理输入一到就把光标"还"回物理屏 | 用过滤驱动把物理鼠标从系统输入栈摘出来，本机光标由自己的覆盖层绘制，系统光标永远留给远端 | `PostMessage` 直接往目标窗口送 `WM_MOUSEMOVE/WM_LBUTTONDOWN`，光标一动不动 |
| 完整鼠标操作 | ✅ 100% 原生（悬停/拖拽/右键菜单/滚轮/拖放/工具提示） | ✅ 原生（远端）+ 本机需自绘（形状/悬停要自己实现） | ❌ 悬停/拖拽/菜单跟踪/`GetCursorPos`/游戏与 Electron 类应用大量失效 |
| 本机看不见远端光标 | ✅ 外屏没有物理输出，天然看不见 | ✅ | ✅ |
| 本机用户无感 | ⚠ 基本无感；**两边同时动**时光标会跟最后一个动的人（见 2.3 边界） | ✅ 完全并行 | ✅ |
| 需要内核驱动 | 不需要 | **需要**（`Interception` 在 Win11 上要 testsigning，且证书已被 EA 反作弊拉黑；`vmulti` 驱动未签名） | 不需要 |
| 失败时的后果 | 钩子挂了 → 本机一切照旧 | 覆盖层挂了 → **本机用户没有光标** | 应用不响应，用户以为"鼠标坏了" |
| 工程量 | 已完成 | 2~4 周（含驱动签名、光标形状/悬停自绘） | 小，但兼容性不可接受 |

**结论：采用 A，并在 A 之上加了"后台定向注入"作为共存路径（§2.5 已实现）。** B 作为阶段二保留（§2.6），
C 只在个别应用上做补充手段。

### 2.3 已实现的方案 A（`CursorArbiter`）

代码：`src/Agent/Agent.Worker/CursorArbiter.cs`，接线在 `Agent.Worker/Program.cs`。

- 远端输入原本就带 `MOUSEEVENTF_ABSOLUTE|MOUSEEVENTF_VIRTUALDESK`，并且**按键/滚轮前先发一次 MOVE**
  （`InputInjector`），所以远端每一次操作都保证光标先落到外屏上的正确像素。
- 新增 `WH_MOUSE_LL` 钩子，**只认自己注入的事件**（`InputInjector` 现在给所有注入事件打了
  `dwExtraInfo = 'RWCTRL01'` 记号 —— 只靠 `LLMHF_INJECTED` 分不清"远端注入"和"触摸板/厂商驱动用
  SendInput 送的输入"，两者待遇正好相反，所以必须打记号）。
- 判定规则（只在采集目标**是虚拟屏**时启用）：
  - 事件是我们注入的 → 原样放行，只记录位置；
  - 物理事件、且光标**不在**外屏上 → 原样放行，零开销、零行为变化；
  - 物理事件、且光标**还停在外屏上**（远端刚用过）→ `SetCursorPos` 把光标还回本机用户上次在物理屏的
    位置（并按本次物理位移补偿一下），然后**把本次按键/滚轮按归还后的坐标重放**（重放事件不带
    `ABSOLUTE`，落点就是刚设好的那个像素，无取整误差），原事件吃掉。
    → **本机用户永远看不见远端光标，点击也永远落在自己的屏上**（否则那一击会打到外屏上他看不见的远端窗口）。
- 顺带接了一个键盘钩子，**只用来判断"本机用户是不是正在用键盘"，从不拦截按键**。
- 失败安全：钩子装不上/钩子内抛异常 → 记一条日志，完全不介入；进程退出自动 `Unhook`。

**边界（写在明处）**：

1. 外屏必须开着（`EnableVirtualDisplay=true`）。若被关掉，远端只能在物理主屏上工作，那时仲裁会反过来
   打断远端，所以**那种配置下不启用仲裁**（`Program.cs` 会打警告）。
2. 两边**同时**操作鼠标时，光标位置是"单例"，谁最后动谁占；本机用户的表现是"光标回到我上次的位置"，
   远端下一次输入会立刻把光标拿回外屏。这是单会话方案的物理上限，不是 bug。
3. **键盘焦点同样是单例**：远端敲的键进的是**当前前台窗口**。所以新增了两道保护：
   - 打开应用时**不再无条件抢前台**（本机用户最近 2.5s 内动过键鼠就跳过，远端点一下窗口即可自行激活）；
   - 本机用户最近 800ms 内动过键鼠时，**远端按键先丢弃**，并限流提示主控端原因
     （宁可远端"暂时打不了字"，也不能把字打进本机用户正在编辑的文档）。
4. 安全桌面（UAC 提权框、锁屏、Ctrl+Alt+Del）里采集与注入都进不去 —— 这是 Windows 的设计，
   主控端会明确提示原因。

### 2.4 远端光标怎么显示：改由主控端自绘

采集端**不再把系统光标烤进画面**（`WgcFrameSource` 关掉 `IsCursorCaptureEnabled`，GDI 兜底路径也删掉了画光标的代码），
远端光标改由**主控端自绘**：`RemoteScreenControl` 在自己的 OnRender 里按"我们最后发给被控端的那个画面坐标"
画一个矢量箭头。

这样处理有两个好处：

1. **被控机上从来没有出现过任何可见的远端光标** —— 本机用户在任何模式下都看不见它（不是靠"藏"，是那里根本没有）；
2. **远端永远看得见自己的指针** —— 尤其是后台定向注入模式下，系统光标压根不在外屏上，靠烤进画面的老做法
   会看到"光标消失"。

### 2.5 双光标（已实现）：本机用户独占真实光标，远端走后台定向注入

这是对 §2.3 的升级。§2.3 里本机用户和远端是**分时抢同一个系统光标**（本机用户一动就"归还"）。
现在再加一条路：**干脆不去碰那个光标**。

**设计**（代码：`Agent.Common/BackgroundInput.cs` + `Agent.Worker/MouseRouter.cs`）

- **本机用户空闲**（默认 1.2 秒内没动键鼠）→ 远端走 **真实光标**：把光标摆到虚拟外屏的坐标上再 `SendInput`。
  悬停、拖拽、原生右键菜单、滚轮、拖放全是 100% 原生；而外屏没有物理输出，本机用户看不见这只光标。
- **本机用户一动手** → 远端**自动切到后台定向注入**：算准"那个位置下面是哪个窗口"
  （`WindowFromPoint` + `RealChildWindowFromPoint` 逐层下钻），把 `WM_MOUSEMOVE` / `WM_LBUTTONDOWN` / …
  **直接 Post 给那个窗口**，**系统光标一根毫毛都不动**。本机用户于是始终独占真实光标，永不被打断。
- **按住左键期间的整段拖拽会锁死路径**，不会中途切换把拖拽弄断；按住期间的移动一律发给"按下的那个窗口"
  （模拟 `SetCapture`）。
- **认领**：远端点过的窗口会被记下来，之后远端打字前先把该窗口带前台（本机用户在忙则直接跳过这次按键，
  见 §2.3 边界 3）—— 否则键会打进本机用户的前台窗口。

**实测结论**（探针 `src/Tests/BgInputProbe`，2026-09-22 六项全过，
原始输出见 `docs/evidence/双光标-后台注入探针-20260922.txt`）

```
[PASS] HitTest 命中按钮自身（期望 hwnd=0x1305E4，实得 0x1305E4）
[PASS] 投递 WM_MOUSEMOVE/LBUTTONDOWN/LBUTTONUP
[PASS] 后台注入点击按钮（目标窗口非前台）：按钮 Click 触发 1 次（期望 1）
[PASS] HitTest 命中文本框自身
[PASS] 投递点击+WM_CHAR
[PASS] 后台注入输入字符：文本框内容 = "A"
==> 探针结论：后台定向注入对标准控件可用
```

关键点：这是在**目标窗口不是前台窗口**的前提下测出来的，而且全程没有调用 `SetCursorPos`/`SendInput` ——
即"不碰系统光标也能点到别人窗口里的按钮"这件事，是**实测成立**的，不是纸上推演。

**和 MouseMux 比**：MouseMux 默认的 Switched 模式是"同一时刻只允许一个人按下去"（其他人被短暂挡住），
并发只对"听话的程序"生效。我们的设计里**本机用户从来不会被挡住**（他永远独占真实光标、永远原生），
被降级的是远端 —— 这正是"主屏不受影响"这条需求要的方向。

**已知边界**（后台注入拿不到的东西，本质都是"合成消息不是可信输入"）：

| 场景 | 能不能用后台注入 | 说明 |
|---|---|---|
| 标准控件（按钮/编辑框/列表/菜单条） | ✅ 实测通过 | 见上面的探针 |
| DuiLib 这类自绘 UI（微信就是） | ✅ 大概率可用 | 它自己在 `WM_MOUSEMOVE` 里做命中测试和悬停自绘 |
| Chromium/Electron（单 HWND） | ✅ 大概率可用 | 顶层窗口过程处理鼠标消息 |
| 原生 `TrackPopupMenu` 右键菜单 | ❌ | 要求窗口在前台、且要真实输入才能跟踪菜单 |
| 依赖 `SetCapture` 的拖拽 | ⚠ 多数可用 | 我们只能"模拟"（按住期间持续投递带 `MK_LBUTTON` 的移动） |
| DirectInput / 原始输入的游戏 | ❌ | 根本不走消息 |
| 区分"合成 vs 可信输入"的程序 | ❌ | 属于对方主动防御 |

以上拿不到的场景，在**本机用户停手 1.2 秒后会自动恢复真实光标**，能力当即可用 —— 也就是
"两边同时用"的代价只落在那段重叠时间里，且只落在远端身上。

**键盘**目前不做后台注入：本机用户空闲 → 真实注入（并先把认领窗口带前台）；本机用户在忙 → 丢掉这次按键
并提示主控端（§2.3 边界 3）。"非前台窗口后台打字"需要把 vk 翻译成字符（`ToUnicodeEx`）+ 自己维护修饰键状态，
是下一步，不是本轮。

**怎么自己验**（会闪两个属于探针自己的小窗口，约 1 秒；它不碰桌面上任何其它程序）：

```bash
DOTNET_ROOT=E:/tools/dotnet \
  RemoteControl/src/Tests/BgInputProbe/bin/Release/net8.0-windows10.0.19041.0/BgInputProbe.exe
```

### 2.6 如果还要更进一步：内核驱动级的真并行

只有一条路：把物理鼠标从系统输入栈里摘出来（内核过滤驱动），本机光标改由自己的覆盖层（Layered Window /
DirectComposition 顶层穿透窗）绘制，系统光标**独占留给远端**。届时两边才能真正同时、互不可见地操作。
代价与风险见 §2.2 B 列 —— 需要驱动签名（客户机器上装内核驱动 + Win11 的 testsigning 限制 + 反作弊拉黑），
以及自绘光标要补齐形状、悬停、提示等细节。**建议在主方案（A）跑稳、且确实出现大量"两边同时用"的场景后再做。**

## 3. 开源调研结论（GitHub）

**没有**任何开源项目直接等于"单会话 + 双独立光标 + 完整鼠标操作"。可复用的积木与最接近的产品：

| 项目 / 产品 | 是什么 | 对我们的价值 |
|---|---|---|
| [MouseMux](https://www.mousemux.com/pages/releases/) | 商业闭源。单会话多光标，多路复用模式，号称"emulates part of the input layer of Windows"，用 Layered Window/DirectComposition 画虚拟光标，且支持 TeamViewer/RustDesk 这类被采集的画面 | **证明方案 B 可行**，也是我们要对标的形态；闭源，不能直接用 |
| [DuoStream/Duo](https://github.com/DuoStream/Duo) | 开源多座位（TermWrap+Sunshine+Moonlight），给每个用户**各自独立的桌面** | 参考其虚拟屏与会话管理；但**独立桌面 = 数据不共享**，不满足我们的产品本意 |
| [neo0oen619/neo_multiseat](https://github.com/neo0oen619/neo_multiseat) | 开源 RDP 多座位脚本（3~10 座） | 同上：RDP = 独立会话 = 不共享 |
| [itsmikethetech/Virtual-Display-Driver](https://github.com/itsmikethetech/Virtual-Display-Driver) | 虚拟显示器驱动（我们已在用 MttVDD） | 现状依赖 |
| [oblitum/Interception](https://github.com/oblitum/Interception) | 键盘/鼠标**过滤驱动**，可摘设备、可注入 | 方案 B 的驱动基座；**Win11 上安装问题多**（需 testsigning、被杀软隔离、证书被 EA 反作弊拉黑），不能作为商业产品依赖 |
| [djpnewton/vmulti](https://github.com/djpnewton/vmulti)、[nefarius/vmulti](https://github.com/nefarius/vmulti)、[xaviersykora/vmulti-win11](https://github.com/xaviersykora/vmulti-win11) | 虚拟 HID 多点设备驱动（多鼠标/多点触控），可在**不移动系统光标**的情况下模拟额外鼠标 | 方案 B 的另一个基座；驱动未签名 |
| [evilC/AutoHotInterception](https://github.com/evilC/AutoHotInterception) | AHK 的设备级输入拦截库 | 原型验证用 |
| [trycua/cua](https://github.com/trycua/cua)（cua-driver-rs v0.5.2） | 开源 Computer-Use Agent 驱动，Windows 上明确做了"**不抢焦点的后台输入** + 多光标 demo" | 方案 C 与"后台输入"的最新实践参考 |

结论：**方案 A 自己实现（已完成）；方案 B 需要自研 + 承担驱动签名风险。** 另外 ASTER / IBIK 这类商用多座位
软件用的是"多会话"，同样不共享一个桌面，不满足"微信拖来拖去"这个验收标准。

## 4. 黑屏：三条已验证的代码级成因（全部已修）

| # | 成因 | 证据 | 修复 |
|---|---|---|---|
| 1 | **采集面失效后无声无息**。WGC 拿不到帧、又没有上一帧可顶时 `return false` 但 `error` 是**空字符串**，而上层只在 `error` 非空时才计数/记录/重建 → 黑屏且日志里**一个字都没有** | `WgcFrameSource.Capture` 原 `return false;` + `Program.cs` 的 `if (!string.IsNullOrEmpty(err))` | 该路径改为返回明确 error 并计数；新增采集项 `Closed` 事件订阅（显示器移除/重建时立刻置失效）；补一条"已 N 秒没有新画面"的限流告警，把"画面静止"和"采集已死"在日志上分开 |
| 2 | **编码器尺寸与采集尺寸脱钩**。ffmpeg 的 `-video_size` 是启动参数、运行期改不了；而采集器尺寸会随显示模式变（打开游戏/播放器改分辨率、外屏重建）→ 喂进去的帧被切碎/ffmpeg 立刻退出 → `RestartEncoder` 又用**同一个错尺寸**重建 → 无限重启、0 帧 | `WgcFrameSource.cs` 会改 `Width/Height`；`Program.cs` 的编码器在 `Start()` 里一次性固定尺寸 | 采集循环里比对 `_source.Width/Height` 与 `_encoder.Width/Height`，不一致就按新尺寸**重建编码器**并发 `StreamReset` |
| 3 | **硬件编码器死了没有退路**。nvenc/qsv/amf 被"打开的应用"抢占/复位 GPU 会话后一直启动失败，而探测结果被 `EncoderCache` **永久缓存**，于是每次重建都拿同一个坏编码器 | `FfmpegEncoder.ResolveEncoder` 的缓存 + `RestartEncoder` 无降级 | 新增 `ForceSoftware()`：连续 3 次重启失败即降级 `libx264`，并在 `ResolveEncoder` 里**先于缓存**生效 |

另外去掉了一处历史风险：`WindowManager.MoveToTargetIfNeeded` 原来对任何窗口都 `ShowWindow(SW_RESTORE)`
（对最大化的/全屏独占的应用会改掉它的显示状态，代码注释里就写着"用户反馈的打开应用后黑屏卡掉"），
现在**只在窗口确实最小化时**才 restore。

> 关于旧多会话方案：它的黑屏来源（mstsc 会话掉线/被最小化 → 无显示表面、安全桌面）随着这条路被封死一起消失。

## 5. CV（剪贴板 / 文件）现状与缺口

**现状（已验收）**

- 文本剪贴板：**双向**，两端各挂 `AddClipboardFormatListener`，靠"剪贴板变化自动同步"＋去重/防回环。
- 文件：**只有"被控端 → 主控端"单向**。在被控端复制文件（`CF_HDROP`）即自动上传到中继
  （`/api/upload`，单文件上限 512 MiB、**10 分钟 TTL**），主控端在画面里按 Ctrl+V 下载。

**共享模式下要注意的一件事**：共享模式的剪贴板就是**本机用户的剪贴板**，所以本机用户复制的东西会被
自动同步给远端。同一个账户下这是预期行为，但**大文件自动上传**会吃被控端上行与服务器磁盘（且无确认）。

**缺口（建议下一步，本轮未动，避免破坏已验收路径）**

1. **主控端 → 被控端**的文件通道完全没有（`src/Viewer` 里没有任何上传代码；协议里的 `0x22 FileChunk`
   只有编解码和单测，是**没接线的死代码**）。要做成"双向"，需要：主控端拖拽/粘贴 → `/api/upload`
   → 新消息通知被控端 → Worker 下载到临时目录 → 写进本会话剪贴板（`CF_HDROP`）。
2. **主控端 Ctrl+V 的语义冲突**：当有远程文件待下载时，`MainWindow.xaml.cs` 会把 Ctrl+V 从"转发给远端"
   里**吞掉**，于是"往远端粘文本"和"取回远端文件"抢同一个按键。建议改成"收到文件通知时**立刻下载并在
   本地剪贴板就位**"，这样 Ctrl+V 就是普通的粘贴，不再需要吞键。
3. 文件传输的**开关与限额**：共享模式下建议增加"自动上传体积上限/确认"，避免误传大文件。

## 7. 验收清单（请在**被控机**上按顺序确认）

前置：被控机已装虚拟显示器驱动；`agent.json` 里 `UseRdpSession=false`（或留 `true` 让程序自动纠正，
启动日志会出现"已强制关闭 → 共享模式"）、`EnableVirtualDisplay=true`、`CursorArbitrationEnabled=true`。

1. 启动后 `coordinator-*.log` 出现：`光标仲裁已启用：外屏=(...)`，且 `显示拓扑` 里能看到那块虚拟屏。
2. 被控机上 `net user` **不再新增**任何用户；`agent.json` 里 `UseRdpSession` 已被改回 `false`。
3. 主控端连上 → 看到的是**本机管理员桌面之外的那块外屏**（不是登录界面、不是黑屏）。
4. 主控端打开微信 → 窗口出现在外屏；**本机用户把同一个微信窗口从物理屏拖到外屏、再拖回来** → 是同一个实例（数据共享）。
5. 主控端在外屏上操作鼠标 → **本机用户看不到任何光标移动/跳变**；本机用户动一下自己的鼠标 → 光标立刻回到他原来的位置，点击落在他自己的屏幕上（不会误触发外屏的程序）。
6. 本机用户正在打字时，主控端连续按键 → 主控端收到"被控端有人正在本机键鼠上操作…"的提示，**本机用户的文档不出现远端字符**。
7. 主控端打开一个会改分辨率的应用（全屏游戏/播放器/模拟器）→ 画面应**自动重建编码器并恢复**；日志出现"采集尺寸变化：… 重建编码器"。若硬件编码器连续失败，日志出现"编码器降级为软件编码 libx264"。
8. 主控端打开一个需要管理员权限的程序 → 画面变黑且键鼠失灵是**预期**（被控机弹出 UAC 安全桌面）；主控端应看到明确原因提示，本机用户点掉 UAC 后画面自动恢复。
9. CV：被控端复制文本/文件 → 主控端可粘贴；主控端复制文本 → 被控端可粘贴。
10. 本机用户空闲时，主控端打开软件 → 窗口被摆到外屏且置前台；**本机用户正在操作时**，不再抢他的前台。
11. **双光标共存**（本轮新增，重点验）：本机用户空闲时，远端在外屏上悬停/右键菜单/拖拽都正常（真实光标路径）；
12. **本机用户同时用自己的鼠标**：他的光标不该被抢走、不该跳动、点击落点正确；同时远端的操作仍然生效
    （自动走后台注入），且主控端画面里远端光标位置正确 —— 这就是"两个光标各自独立"的验收点；
13. 本机用户同时在打字：主控端收到"被控端有人正在本机键鼠上操作…"的提示，且本机用户的文档里不出现远端字符；
14. 被控端日志里能看到路径切换：`鼠标路径 → 后台定向注入（本机用户正在操作…）`
    与 `鼠标路径 → 真实光标（本机用户已停手…）`。
